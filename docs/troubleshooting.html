Troubleshooting

Common issues encountered while configuring, running, or contributing to the BL Crop Raid Report workflow, and how to resolve them. If your issue isn't listed here, open an issue on GitHub.

Configuration & Connections

Workflow errors out with no events found

The event fetch sets raise_on_empty: true, so if EarthRanger has zero hwc_crop_raids events for your selected time range, the workflow raises an explicit error rather than completing with empty outputs. Widen the time range or confirm the events exist under that event type in EarthRanger.

EarthRanger connection fails or times out

Verify the server URL, username, and password configured in the EarthRanger Connection. Confirm you can log into that same EarthRanger instance directly in a browser with the same credentials. Credentials aren't validated at setup time, so an invalid password only surfaces as an error once the workflow actually runs.

Amboseli geospatial layers or the Word template fail to download

The three Amboseli GeoPackages and the Word report template are fetched from fixed Dropbox share links in spec.yaml. These links carry an expiring share token (st= parameter); if a link has been rotated or revoked on Dropbox's side, fetch_and_persist_file will exhaust its 3 retries and fail. This isn't a workflow configuration issue — the URLs in spec.yaml would need to be refreshed.

Charts & Tables

"French beans" incidents show up under "Other" in the top-crops charts

This is expected given the current spec.yaml: the total_incidents_recorded and total_damage_recorded charts group crops into Beans, Maize, Onion, Tomatoes, Watermelon, and Other. French beans has its own colour defined elsewhere in the workflow's colour map, but the grouping step for these two charts folds it into "Other" rather than giving it its own bucket — see the Technical Guide, §4.6.

total_damage_recorded's "Acres" totals look inflated or inconsistent with the damage boxplot

Unlike the damage boxplot and the crop-damage pie chart, total_damage_recorded is not filtered to Measurement unit == "Acre" in the current spec.yaml — a filter_acre_aoo task exists for this purpose but its output is never used downstream. If your EarthRanger data records some crop-raid damage in non-acre units (e.g. plots, rows), those values are included in this chart despite its "Acres" axis label. Treat the chart as indicative rather than a strict acreage total until the spec is updated to use the filtered dataframe.

Crop species pie charts (§4.4/§4.5) look empty or very sparse

Both pie charts are restricted to Core AOO events where Damage caused = "Yes". If most of your period's incidents were logged outside the Core AOO, or without a confirmed "Damage caused" value, these two charts will have little or no data even though the raw event count is high. This is expected scoping, not a bug — the monthly location chart (§4.3) and the summary tables use the full dataset for comparison.

Elephant summary tables don't match a manual Core-AOO-only count

The two elephant tables (total_land_size_damaged_by_elephants, average_elephant_group_size_over_time) are filtered to Species responsible == "Elephant" and Measurement unit == "Acre", but are not restricted to Core AOO — they cover elephant incidents across all crop raid locations. If you're cross-checking against a Core-AOO-only figure, the totals won't match by design.

Maps

A month is missing from the per-month crop-destroyed map widget

The per-month maps are generated by splitting events on the calendar month name; a month with no crop raid events in your selected time range simply produces no view for that month in the merged widget. This is expected fan-out behaviour, not a failure.

Map PNG is blank, cut off, or missing in the Word report

All map screenshots (density grid, response timing, species, and per-month crop maps) wait 40 000 ms for the basemap tiles to load before capturing the screenshot — far longer than the 1 ms wait used for the batched Plotly charts, which render client-side without external tile requests. On a slow network this can still be insufficient for a consistently complete tile render.

Report & Dashboard

Word report is missing an image, or fails to generate

If any upstream chart or PNG conversion failed or was skipped (e.g. due to an empty dataframe for a given filter), report generation can fail or produce a document with a missing image. Check the run logs for skipped tasks upstream of generate_report.

Word report always says "Generated by Ecoscope"

This is expected — generated_by is a fixed string in spec.yaml, not looked up from the EarthRanger user who ran the workflow.

No outputs written / can't find results

All outputs are written to the directory specified by the ECOSCOPE_WORKFLOWS_RESULTS environment variable. Confirm it's set and points to a directory the workflow process can write to.

Contributing & CI

These apply if you're modifying the workflow itself (spec.yaml, test-cases.yaml, or the generated ecoscope-workflows-bl-crop-raid-report-workflow/ directory) and opening a pull request.

ecoscope-workflows-bl-crop-raid-report-workflow/ is missing from your checkout

This generated directory is tracked in git but can be absent from a local working tree (e.g. after a partial checkout or an interrupted recompile). Regenerate it before committing anything:

pixi run --manifest-path pixi.toml --locked bash -c "./dev/recompile.sh --update"

Generated files differ from committed files in ecoscope-workflows-bl-crop-raid-report-workflow

The generated workflow directory is out of sync with spec.yaml. Run the recompile script locally and commit the result (same command as above).

test-cases.yaml references a calculator task that doesn't exist in this workflow

The current test-cases.yaml still contains calculator parameters (a, b, operation) left over from the workflow scaffold — spec.yaml has no task with that id. If you're updating test cases, replace these with parameters for the tasks this workflow actually exposes (workflow_details, time_range, and er_client_name).

Found wildcard version (*) in requirements or Found local file channel (file://) in requirements

In spec.yaml, every dependency under requirements must pin an exact version and use a remote conda channel — wildcard versions and local file:// channels are only valid for local development, not for CI using published packages.

VERSION.yaml (...) must be greater than main branch (...)

Bump MAJ/MIN/PATCH in ecoscope-workflows-bl-crop-raid-report-workflow/VERSION.yaml so it's strictly greater than the version on main before opening or updating a PR.

Workflow tests fail in CI but pass locally (or vice versa)

test.yml runs test cases against all of ubuntu-latest, macos-latest, and windows-latest. If a test only fails on CI, check whether it depends on EarthRanger credentials being available as secrets, or on OS-specific path handling.
